# Redesign an app from this design system (agent workflow)

This guide lets a developer point an AI coding agent at this repository and have
it restyle a Next.js (or other web) app to the ForEveryone design system from a
single careful prompt. It implements the approach in Evil Martians' chronicle
*Building a design system specced for engineers and agents*: a single
machine-readable source of truth, one correct answer per decision, and OKLCH so
the agent can extend colour deterministically.

## What the agent reads (in order)

1. [`llms.txt`](../../llms.txt) — entry point and hard rules.
2. [`spec/tokens.json`](../../spec/tokens.json) — every token resolved, with its
   CSS variable name and `surface` ("digital" | "print").
3. [`spec/principles.md`](../../spec/principles.md) — deterministic colour, type,
   layout, and digital-vs-print rules.
4. [`spec/components/`](../../spec/components/) — per-component contracts (one
   correct class, states, do/don't).
5. [`css/custom-properties.css`](../../css/custom-properties.css) — the variables
   to import.

## Adoption steps

1. **Import the variables.** Copy `css/custom-properties.css` into the target app
   (or vendor it) and import it once at the root. All styling references
   `var(--*)`.
2. **Map ad-hoc colours to tokens.** Replace raw hex/rgb in the target app with
   the nearest token by role (background, text, accent). Use only the approved
   background ⇄ text pairings in `spec/principles.md`.
3. **Extend, don't invent.** If a needed shade is missing, derive it in OKLCH:
   hold the token's hue and lightness, step the chroma. Never introduce a new hex
   literal.
4. **Rebuild components against contracts.** Restyle buttons, cards, inputs,
   tags, and accordions to the `spec/components/*.md` classes and states.
5. **Apply type + layout rules.** Filson Pro digital only (Young Serif is print);
   roles and the ≥1.5 body line-height; left-aligned, generous white space.
6. **Verify.** Run the target app's a11y checks; confirm no `surface:"print"`
   token is referenced, no Orange text background, and all body text meets the
   documented contrast ratios.

## Guardrails (the agent must refuse to)

- Invent hex values or font names.
- Use `surface:"print"` tokens on the web (`--font-family-accent`,
  `--color-print-*`, `--color-doc-*`).
- Use Orange as a text/background fill, or white text on a light tint.
- Use Blue for anything other than announcements/alerts (with white text).
- Drop visible keyboard focus or ignore `prefers-reduced-motion`.

## Ready-to-paste prompt

```text
You are restyling THIS Next.js app to the ForEveryone Berlin design system.

Source of truth: the design-system repo at <path-or-URL>. Read, in order:
llms.txt, spec/tokens.json, spec/principles.md, spec/components/*.md, and
css/custom-properties.css. Treat them as authoritative.

Do:
- Import css/custom-properties.css once at the app root.
- Replace every ad-hoc colour, font, radius, and spacing value with the nearest
  token by ROLE (resolve names/values from spec/tokens.json).
- Rebuild buttons, cards, inputs, tags, and accordions to the .fe-* contracts in
  spec/components, including their states.
- Apply the colour, typography, and layout rules in spec/principles.md exactly.

Never:
- Invent hex values or font names — extend palettes in OKLCH (hold hue +
  lightness, step chroma).
- Use any token whose surface is "print" on the web.
- Put text on an Orange background, or white text on a light tint.
- Use Blue outside announcements/alerts.

Then verify: run the app, check the documented contrast ratios hold, keyboard
focus is visible, prefers-reduced-motion is respected, and report a token-by-
token mapping of what you changed.
```

## Keeping it honest

`spec/tokens.json` is generated by `node scripts/build-spec.js` from `tokens/`,
so it never drifts from the source tokens. Regenerate it whenever tokens change
(alongside `node scripts/build-css.js`).
